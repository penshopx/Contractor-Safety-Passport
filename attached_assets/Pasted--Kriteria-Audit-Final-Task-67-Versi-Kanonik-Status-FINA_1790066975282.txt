## Tujuan Inti

Kegagalan sementara dipulihkan secara otomatis. Kegagalan permanen atau retry yang habis masuk ke kondisi terminal yang aman, tetap memblokir penggunaan undangan, dan memerlukan pemulihan manual terotorisasi. Sistem menjamin **safe failure**, bukan keberhasilan otomatis tanpa batas.

## 1. State Machine Persisten

### Transisi Lengkap

```text
NONE
  → PENDING_REVOKE
      (saat finalisasi database gagal setelah Clerk berhasil membuat undangan)

PENDING_REVOKE | REVOKE_FAILED
  → REVOKED
      (revoke Clerk berhasil, atau respons semantik menunjukkan sudah tidak aktif)
  → REVOKE_FAILED
      (revoke Clerk gagal sementara — self-transition untuk retry berturut-turut)
  → REVOKE_PERMANENTLY_FAILED
      (revoke Clerk gagal permanen — 4xx non-retryable)
  → DEAD_LETTER
      (retry_count mencapai batas maksimum)

REVOKE_PERMANENTLY_FAILED | DEAD_LETTER
  → PENDING_REVOKE
      (hanya melalui retry manual terotorisasi oleh owner organisasi)
```

### Kriteria Tinggi

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 1.1 | State machine mengikuti transisi lengkap di atas tanpa pengecualian | Tes state machine: setiap transisi legal valid, setiap transisi ilegal ditolak |
| 1.2 | Self-transition `REVOKE_FAILED → REVOKE_FAILED` didukung untuk retry berturut-turut yang tetap gagal sementara | Tes: 3 retry gagal berturut-turut → status tetap `REVOKE_FAILED`, `retry_count` bertambah |
| 1.3 | Lease worker disimpan terpisah dari status bisnis: kolom `lease_owner`, `lease_expires_at`, `claim_token` | Schema database menunjukkan kolom terpisah |
| 1.4 | Transisi status atomik dalam transaksi database | Tes konkurensi: 2 worker coba transisi bersamaan, hanya 1 berhasil |
| 1.5 | Worker yang crash di tengah transisi tidak meninggalkan status ambigu | Tes: kill proses saat update status, restart → status konsisten |

### Kriteria Sedang

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|

## 2. Atomic Claim & Idempotensi

### Predicate Claim

Worker mengklaim job dengan query atomic berikut:

```sql
UPDATE invitations
SET 
  compensation_status = compensation_status,
  lease_owner = $worker_id,
  lease_expires_at = NOW() + $lease_duration,
  claim_token = gen_random_uuid(),
  compensation_updated_at = NOW()
WHERE id = $invitation_id
  AND compensation_status IN ('PENDING_REVOKE', 'REVOKE_FAILED')
  AND next_retry_at <= NOW()
  AND (lease_expires_at IS NULL OR lease_expires_at <= NOW())
RETURNING id, claim_token, clerk_invitation_id, correlation_id;
```

Jika `RETURNING` kosong, worker tidak mendapat lease dan langsung berhenti.

### Kriteria Tinggi

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 2.1 | Predicate claim mencakup `lease_expires_at IS NULL` agar job baru dapat diklaim | Tes: job baru dengan `lease_expires_at = NULL` berhasil diklaim |
| 2.2 | Predicate menggunakan `<=` untuk `lease_expires_at` dan `next_retry_at` | Audit query SQL |
| 2.3 | Atomic update menghasilkan `claim_token` baru, mengisi `lease_owner` dan `lease_expires_at`, mengembalikan baris yang diklaim | Tes: RETURNING mengembalikan baris dengan claim_token baru |
| 2.4 | Finalisasi hanya dilakukan oleh worker yang masih memegang `claim_token` yang sama | Tes: finalisasi dengan claim_token berbeda → ditolak |
| 2.5 | Lease dibersihkan setelah finalisasi berhasil atau gagal | Tes: setelah finalisasi, kolom lease NULL |
| 2.6 | Respons Clerk yang secara semantik menunjukkan undangan "sudah tidak aktif", "tidak ditemukan", atau "sudah dicabut" diperlakukan sebagai keberhasilan idempoten → status = `REVOKED` | Tes: mock error sesuai SDK Clerk → status = `REVOKED` |
| 2.7 | Retry hanya untuk status `PENDING_REVOKE` atau `REVOKE_FAILED` | Tes: coba claim job `NONE` → tidak ada baris dikembalikan |

### Kriteria Sedang

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 2.8 | Tes meniru bentuk error sebenarnya dari versi Clerk SDK yang dipakai | Audit test menunjukkan mock error sesuai SDK |

### Batasan Eksplisit

- Tidak perlu idempotency key untuk revoke (kecuali SDK Clerk terbukti mendukung)
- Tidak perlu distributed lock (optimistic locking via lease sudah cukup)

## 5. Klasifikasi Kegagalan

### Kategori Klasifikasi

| Kategori | Kondisi | Hasil Status |
|----------|---------|-------------|
| **Terminal-success** | Respons semantik Clerk: not found, already revoked, atau inactive | `REVOKED` |
| **Retryable** | Timeout, network error, HTTP `408`, HTTP `429`, HTTP `5xx` | `REVOKE_FAILED` |
| **Permanent** | HTTP `4xx` lain yang menunjukkan request tidak dapat berhasil tanpa perubahan | `REVOKE_PERMANENTLY_FAILED` |
| **Unknown** | Error tidak terklasifikasi | Default ke retryable dengan batas retry |
