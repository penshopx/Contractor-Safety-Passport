Baik, saya bahas task ini dengan disiplin yang sama — sebagai bahan audit, bukan panduan implementasi mentah.

## Skenario Kegagalan yang Harus Ditutup

Lost update pada status kesiapan dapat terjadi dalam beberapa mode:

| Mode kegagalan | Dampak |
|---|---|
| Dua ahli K3 edit status proyek hampir bersamaan | Perubahan ahli pertama hilang tanpa disadari |
| Ahli K3 edit lama, simpan setelah rekan lain update | Perubahan rekan tertimpa |
| Ahli K3 tidak sadar ada perubahan terbaru | Status kesiapan final tidak mencerminkan semua input |
| Disconnect lalu reconnect | Ahli K3 tidak tahu ada perubahan selama offline |
| Multiple proyek diedit sekaligus | Satu request simpan menimpa perubahan di proyek lain |
| Edit bagian berbeda dari status kesiapan | Seharusnya bisa digabung, tapi malah ditolak |

Kasus kritis di konteks K3: status kesiapan yang salah bisa berakabat pada penilaian CSMS yang tidak akurat, yang mempengaruhi keputusan principal (PLN/Pertamina) terhadap kontraktor.

## Prinsip Kontrol Versi untuk Status Kesiapan

### 1. Version Number per Proyek

Setiap proyek punya version number untuk status kesiapan yang berubah setiap kali ada perubahan:
- Version number disimpan bersama status kesiapan
- Client wajib mengirim version number yang terakhir dibaca saat menyimpan
- Server cek: apakah version number masih sama?
  - Jika sama → simpan, increment version number
  - Jika berbeda → tolak dengan error "konflik versi"

### 2. Optimistic Concurrency Control

Pola yang cocok untuk kolaborasi tanpa locking:
- Ahli K3 mengambil status kesiapan + version number
- Ahli K3 edit secara lokal
- Ahli K3 kirim simpan dengan status + version number asli
- Server cek version number
- Jika cocok → simpan
- Jika tidak cocok → tolak dengan `409 Conflict`

### 3. Granularitas Update

Status kesiapan kemungkinan terdiri dari beberapa bagian:
- Kesiapan dokumen
- Kesiapan personel
- Kesiapan peralatan
- Kesiapan prosedur
- dll.

Pertanyaan penting:
- Apakah version number per proyek keseluruhan, atau per bagian?
- Jika per proyek: edit bagian berbeda tetap konflik
- Jika per bagian: edit bagian berbeda bisa auto-merge

### 4. Penanganan Konflik yang Eksplisit

Saat konflik terdeteksi, user harus diberi opsi yang jelas:
- **Muat ulang versi terbaru** — kehilangan perubahan lokal
- **Gabungkan secara manual** — tampilkan diff, user pilih
- **Batal** — kembali ke editor tanpa menyimpan

### 5. Auto-Merge untuk Bagian Berbeda

Jika ahli A edit "kesiapan dokumen" dan ahli B edit "kesiapan personel":
- Server bisa deteksi bahwa perubahan tidak overlap
- Auto-merge: gabungkan kedua perubahan
- Version number tetap increment

### 6. Metadata Perubahan

Setiap perubahan status kesiapan harus mencatat:
- Siapa yang mengubah (`updated_by`)
- Kapan diubah (`updated_at`)
- Version number setelah perubahan

Ini penting untuk audit trail dan debugging konflik.

## Test Case yang Diperlukan

### Test Dasar

1. **Dua ahli K3 simpan hampir bersamaan**
   - Ahli A dan Ahli B buka status kesiapan Proyek X (versi 1)
   - Ahli A simpan perubahan → berhasil, versi jadi 2
   - Ahli B simpan perubahan → ditolak dengan error "konflik versi"
   - Ahli B diberi opsi: muat ulang atau gabungkan

2. **Muat ulang versi terbaru**
   - Ahli B pilih "muat ulang"
   - Status kesiapan lokal diganti dengan versi 2 dari server
   - Perubahan lokal Ahli B hilang
   - Ahli B bisa edit lagi dari versi terbaru

3. **Gabungkan secara manual**
   - Ahli B pilih "gabungkan"
   - Tampilkan diff: perubahan Ahli A vs perubahan lokal Ahli B
   - Ahli B pilih per bagian: pakai versi A atau versi lokal
   - Setelah merge, simpan berhasil, versi jadi 3

4. **Edit bagian berbeda, auto-merge**
   - Ahli A edit "kesiapan dokumen", Ahli B edit "kesiapan personel"
   - Ahli A simpan → berhasil
   - Ahli B simpan → auto-merge (karena bagian berbeda)
   - Versi jadi 2, kedua perubahan tersimpan

### Test Edge Cases

5. **Multiple conflicts berantai**
   - Ahli A, B, C buka status kesiapan versi 1
   - Ahli A simpan → versi 2
   - Ahli B simpan → konflik, muat ulang versi 2, edit, simpan → versi 3
   - Ahli C simpan → konflik, muat ulang versi 3, edit, simpan → versi 4
   - Semua perubahan tersimpan tanpa lost update

6. **Disconnect dan reconnect**
   - Ahli A buka status kesiapan versi 1
   - Ahli A disconnect (offline)
   - Ahli B simpan perubahan → versi 2
   - Ahli A reconnect, simpan perubahan → konflik
   - Ahli A diberi opsi: muat ulang atau gabungkan

7. **Race condition simulasi**
   - Dua request simpan dikirim pada waktu yang hampir sama
   - Database transaction atau optimistic locking mencegah lost update
   - Salah satu request berhasil, yang lain ditolak

8. **Version number overflow**
   - Version number mencapai batas maksimum (jika pakai integer)
   - Bagaimana handle? Wrap around? Error?
   - Kebijakan eksplisit

9. **Proyek dihapus saat user edit**
   - Ahli A buka status kesiapan
   - Proyek dihapus (jika diizinkan)
   - Ahli A simpan → error "proyek tidak ditemukan"
   - Bukan lost update, tapi error eksplisit

10. **Isolasi organisasi**
    - Organisasi A punya Proyek X dengan status kesiapan versi 1
    - Organisasi B punya Proyek X dengan status kesiapan versi 1
    - Update di organisasi A tidak mempengaruhi organisasi B

## Checklist Audit

### A. Kontrol Versi
- [ ] Status kesiapan punya version number yang berubah setiap kali ada perubahan
- [ ] Setiap simpan menyertakan version number yang diedit
- [ ] Server cek version number sebelum simpan
- [ ] Jika version tidak cocok, tolak dengan error eksplisit (`409 Conflict`)
- [ ] Version number increment setelah simpan berhasil

### B. Granularitas Update
- [ ] Kebijakan eksplisit: version per proyek keseluruhan atau per bagian?
- [ ] Jika per bagian: auto-merge untuk bagian berbeda
- [ ] Jika per proyek: semua edit menyebabkan konflik

### C. Penanganan Konflik
- [ ] User diberi opsi: muat ulang, gabungkan, atau batal
- [ ] UI menampilkan diff antara versi lokal dan versi terbaru
- [ ] User bisa pilih perubahan per bagian (versi lokal vs versi remote)
- [ ] Setelah merge, version number diperbarui
- [ ] Pesan error jelas dan dapat ditindaklanjuti

### D. Auto-Merge
- [ ] Jika perubahan tidak overlap (bagian berbeda), auto-merge dilakukan
- [ ] Auto-merge tidak menyebabkan lost update
- [ ] User diberi notifikasi bahwa auto-merge dilakukan

### E. Metadata Perubahan
- [ ] Setiap perubahan mencatat `updated_by` (siapa yang mengubah)
- [ ] Setiap perubahan mencatat `updated_at` (kapan diubah)
- [ ] Metadata ditampilkan di UI untuk transparansi

### F. Race Condition
- [ ] Simpan simultan ditangani dengan database transaction atau optimistic locking
- [ ] Tidak ada lost update bahkan jika dua request tiba pada waktu yang hampir sama
- [ ] Test konkurensi membuktikan tidak ada race condition

### G. Edge Cases
- [ ] Multiple conflicts berantai ditangani dengan benar
- [ ] Disconnect dan reconnect → konflik terdeteksi saat reconnect
- [ ] Version number overflow → kebijakan eksplisit
- [ ] Proyek dihapus saat user edit → error eksplisit

### H. Isolasi Organisasi
- [ ] Status kesiapan terisolasi per organisasi
- [ ] Update di organisasi A tidak mempengaruhi organisasi B
- [ ] FK atau validasi API memastikan isolasi

### I. UX
- [ ] Diff viewer mudah dipahami (bagian yang diubah)
- [ ] Tombol "muat ulang", "gabungkan", "batal" jelas
- [ ] Indikator loading saat memuat versi terbaru
- [ ] Pesan error dalam bahasa yang user-friendly

### J. Testing
- [ ] Test dua ahli K3 simpan simultan → konflik terdeteksi
- [ ] Test conflict resolution (muat ulang dan gabungkan)
- [ ] Test auto-merge untuk bagian berbeda
- [ ] Test multiple conflicts berantai
- [ ] Test disconnect/reconnect
- [ ] Test race condition dengan request simultan

### K. Monitoring
- [ ] Metric: jumlah konflik yang terdeteksi per hari
- [ ] Metric: berapa user pilih muat ulang vs gabungkan
- [ ] Metric: waktu rata-rata untuk resolve konflik
- [ ] Alert jika jumlah konflik meningkat drastis

## Pertimbangan yang Perlu Dikonfirmasi

Beberapa hal yang perlu diverifikasi saat audit:

1. **Struktur data status kesiapan**: Apakah disimpan sebagai satu dokumen JSON, atau sebagai field-field terpisah?
2. **Granularitas version**: Per proyek keseluruhan atau per bagian?
3. **Jumlah bagian status kesiapan**: Berapa banyak bagian yang bisa diedit independen?
4. **Stack database**: PostgreSQL, MongoDB, atau lainnya? Ini mempengaruhi cara implementasi optimistic locking.
5. **Jumlah user tipikal**: Berapa banyak ahli K3 yang biasanya edit status kesiapan proyek yang sama?
