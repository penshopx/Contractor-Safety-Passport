# Kriteria Audit Final — Task #67 (Revisi Final)

## Tujuan Inti

Kegagalan sementara dipulihkan secara otomatis. Kegagalan permanen atau retry yang habis masuk ke kondisi terminal yang aman, tetap memblokir penggunaan undangan, dan memerlukan pemulihan manual terotorisasi. Sistem menjamin **safe failure**, bukan keberhasilan otomatis tanpa batas.

---

## 1. State Machine Persisten (Revisi: Transisi Lengkap + Lease Terpisah)

### Kriteria Tinggi

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 1.1 | Status kompensasi tersimpan di database dengan transisi lengkap: `NONE` → `PENDING_REVOKE` → (`REVOKED` \| `REVOKE_FAILED` \| `REVOKE_PERMANENTLY_FAILED` \| `DEAD_LETTER`) | Tes state machine: semua transisi legal valid, transisi ilegal ditolak |
| 1.2 | Lease worker disimpan terpisah dari status bisnis: `lease_owner`, `lease_expires_at`, `claim_token` | Schema database menunjukkan kolom terpisah |
| 1.3 | Transisi status atomik dalam transaksi database | Tes konkurensi: 2 worker coba transisi bersamaan, hanya 1 berhasil |
| 1.4 | Worker yang crash di tengah transisi tidak meninggalkan status ambigu | Tes: kill proses saat update status, restart → status konsisten |
| 1.5 | Lease claim memakai optimistic locking: `UPDATE ... WHERE status = ? AND lease_expires_at < NOW()` | Query menunjukkan atomic claim |

### Kriteria Sedang

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 1.6 | Timestamp setiap transisi dicatat (`compensation_updated_at`) | Query menunjukkan waktu perubahan |
| 1.7 | Alasan transisi dicatat (`compensation_reason`): `FINALIZATION_FAILED`, `REVOKE_FAILED`, `RETRY_SUCCESS`, `MANUAL_OVERRIDE` | Nilai enum sesuai |

### Batasan Eksplisit

- Lease metadata bukan status bisnis tambahan
- Tidak perlu saga pattern atau distributed transaction

## 2. Idempotensi via Atomic Claim (Revisi: Tanpa Asumsi Idempotency Key Clerk)

### Kriteria Tinggi

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 2.1 | Worker memenangkan atomic database claim sebelum memanggil Clerk | Tes: 2 worker paralel, hanya 1 yang mendapat lease |
| 2.2 | Worker lain tidak boleh revoke selama lease aktif | Tes: worker kedua langsung return tanpa panggil Clerk |
| 2.3 | Finalisasi hanya dilakukan oleh worker yang masih memegang claim token | Tes: claim token tidak cocok → finalisasi ditolak |
| 2.4 | Respons Clerk yang menunjukkan undangan "sudah tidak aktif", "tidak ditemukan", atau "sudah dicabut" diperlakukan sebagai keberhasilan idempoten → status = `REVOKED` | Tes: mock error "not found" dari SDK Clerk → status = `REVOKED` |
| 2.5 | Retry hanya untuk status `PENDING_REVOKE` atau `REVOKE_FAILED` | Tes: coba revoke undangan `NONE` → ditolak |

### Kriteria Sedang

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 2.6 | Tes meniru bentuk error sebenarnya dari versi Clerk SDK yang dipakai, bukan asumsi status HTTP | Audit test menunjukkan mock error sesuai SDK |

### Batasan Eksplisit

- Tidak perlu idempotency key untuk revoke (kecuali SDK Clerk terbukti mendukung)
- Tidak perlu distributed lock (optimistic locking via lease sudah cukup)

## 4. Klasifikasi Kegagalan (Revisi: Tanpa Asumsi HTTP Status)

### Kriteria Tinggi

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 4.1 | Kegagalan jaringan Clerk diklasifikasikan sebagai `RETRYABLE` → status = `REVOKE_FAILED` | Tes: mock timeout → status = `REVOKE_FAILED` |
| 4.2 | Kegagalan 5xx Clerk diklasifikasikan sebagai `RETRYABLE` | Tes: mock 500 → status = `REVOKE_FAILED` |
| 4.3 | Kegagalan 4xx Clerk (selain "not found"/"already revoked") diklasifikasikan sebagai `PERMANENT` → status = `REVOKE_PERMANENTLY_FAILED` | Tes: mock 400 → status = `REVOKE_PERMANENTLY_FAILED` |
| 4.4 | Job `PERMANENT` tidak di-retry otomatis | Tes: worker tidak ambil job `REVOKE_PERMANENTLY_FAILED` |

### Kriteria Sedang

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 4.5 | Error message Clerk disimpan untuk debugging (tanpa token) | Audit log menunjukkan error message |
| 4.6 | Rate limit Clerk (429) diklasifikasikan sebagai `RETRYABLE` dengan backoff panjang | Tes: mock 429 → delay lebih lama |

### Batasan Eksplisit

- Tidak perlu circuit breaker
- Tidak perlu granular error classification (retryable vs permanent sudah cukup)

## 5. Backoff, Retry Limit, & Dead-Letter (Revisi: Konsisten dengan Safe Failure)

### Kriteria Tinggi

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 5.1 | Retry memakai exponential backoff (1s, 2s, 4s, 8s, ...) | Tes: cek delay antar retry |
| 5.2 | Backoff memiliki batas atas (max 5 menit) | Tes: retry ke-10 masih delay 5 menit |
| 5.3 | Batas retry maksimum (default 10 kali) | Tes: setelah 10 retry → status = `DEAD_LETTER` |
| 5.4 | Job `DEAD_LETTER` tidak di-retry otomatis | Tes: worker tidak ambil job `DEAD_LETTER` |
| 5.5 | Endpoint admin untuk retry manual job `DEAD_LETTER` | Tes: POST `/organizations/:orgId/compensations/:id/retry` → status = `PENDING_REVOKE` |
| 5.6 | Endpoint retry manual TIDAK memanggil Clerk sinkron, hanya ubah status dan reset metadata retry | Tes: endpoint return cepat, worker yang proses |

### Kriteria Sedang

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 5.7 | Jitter ditambahkan ke backoff | Tes: 10 retry paralel delay sedikit berbeda |
| 5.8 | Endpoint admin untuk lihat daftar job `DEAD_LETTER` | GET `/organizations/:orgId/compensations?status=DEAD_LETTER` |
| 5.9 | Retry manual tercatat di audit log | Audit log menunjukkan `MANUAL_OVERRIDE` |

### Batasan Eksplisit

- Tidak perlu integrasi alerting eksternal
- Tidak perlu dead-letter queue terpisah

## 6. Safety: Undangan Terkunci Selama Kompensasi (Revisi: Jaminan Realistis)

### Kriteria Tinggi

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 6.1 | Undangan status `PENDING_REVOKE`, `REVOKE_FAILED`, `REVOKE_PERMANENTLY_FAILED`, `DEAD_LETTER` tidak dapat diterima user | Tes: coba accept → ditolak |
| 6.2 | Undangan status kompensasi tidak muncul di daftar undangan aktif | Tes: GET `/invitations` tidak mengembalikan |
| 6.3 | Email undangan status kompensasi tidak dapat diundang ulang sampai kompensasi selesai atau dipulihkan resmi | Tes: coba invite email sama → error "compensation in progress" |
| 6.4 | Undangan status kompensasi tidak dapat menghasilkan membership lokal | Tes: accept ditolak → tidak ada baris membership |
| 6.5 | Worker tetap mencoba revoke di Clerk sesuai kebijakan retry | Tes: job `REVOKE_FAILED` di-retry worker |

### Kriteria Sedang

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 6.6 | UI menampilkan pesan jelas jika user coba accept undangan yang sedang dikompensasi | Tes UI: pesan "Undangan sedang diproses" |

### Batasan Eksplisit

- Sistem tidak mengklaim status eksternal Clerk sudah sinkron sebelum Clerk konfirmasi
- Database lokal tidak bisa guarantee Clerk sudah nonaktifkan undangan jika revoke gagal
- Tidak perlu email notifikasi ke user tentang status kompensasi

## 8. Persistensi Baris Reservasi (Revisi: Jaminan Durable)

### Kriteria Tinggi

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 8.1 | Setelah Clerk berhasil membuat undangan, kegagalan finalisasi secara atomik meninggalkan catatan `PENDING_REVOKE` | Tes: mock finalisasi gagal → baris tetap ada dengan status `PENDING_REVOKE` |
| 8.2 | Catatan menyimpan: `clerk_invitation_id`, `organization_id`, status, `retry_count`, `next_retry_at`, lease metadata | Schema database menunjukkan kolom lengkap |
| 8.3 | Baris menjadi sumber state machine sekaligus penghalang acceptance dan re-invite | Tes: baris ada → accept ditolak, re-invite ditolak |
| 8.4 | Baris hanya dihapus atau diarsipkan setelah status `REVOKED`, sesuai kebijakan retensi | Tes: status bukan `REVOKED` → baris tidak dihapus |
| 8.5 | Kegagalan revoke tidak mencegah persistensi status kompensasi | Tes: mock revoke gagal → status tetap tersimpan |

### Kriteria Sedang

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 8.6 | Kebijakan retensi untuk baris `REVOKED` dapat dikonfigurasi | Environment variable atau config |

### Batasan Eksplisit

- Baris tidak boleh dihapus sebelum revoke Clerk dikonfirmasi
- Bukti pekerjaan tidak boleh hilang
