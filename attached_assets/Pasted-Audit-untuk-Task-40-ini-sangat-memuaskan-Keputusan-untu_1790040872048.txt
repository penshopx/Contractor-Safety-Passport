Audit untuk **Task #40** ini sangat memuaskan. Keputusan untuk menggunakan **Atomic Database Reservation** (`INSERT ... ON CONFLICT DO NOTHING`) alih-alih *Advisory Lock* atau *Idempotency Key* adalah pilihan arsitektur yang sangat elegan. Ini memindahkan beban konkurensi ke tempat yang paling tepat: **Database Engine (PostgreSQL)**, yang menjamin ACID properties tanpa perlu mengelola *state* di level aplikasi atau koneksi pool.

Namun, temuan **Medium** mengenai *Zombie Reservations* (reservasi tertinggal saat proses crash) dan *Split-Brain* (kegagalan revoke Clerk) adalah risiko nyata di lingkungan produksi. Mari kita selesaikan kedua masalah ini sebelum beralih ke audit **Task #41**.

### 1. Solusi untuk Temuan Task #40 (Sebelum Ditutup)

#### A. Mengatasi "Zombie Reservations" (Process Crash)
Jika server crash setelah `INSERT` reservasi tetapi sebelum panggilan Clerk selesai, baris tersebut akan terkunci selamanya karena `clerkInvitationId = null` dan `acceptedAt/revokedAt = null`.

**Solusi: Pola "Self-Healing Insert" (Tanpa Background Worker)**
Daripada membuat *cron job* untuk membersihkan zombie, kita bisa membuat logika *insert* yang menyembuhkan dirinya sendiri:

1. Tambahkan kolom `reserved_at TIMESTAMP DEFAULT NOW()` pada tabel `invitations`.
2. Saat aplikasi menangkap error *Unique Violation* (409), jangan langsung lempar error ke user. Lakukan investigasi:
   ```typescript
   try {
     await insertReservation(orgId, email);
   } catch (error) {
     if (isUniqueViolation(error)) {
       // Cari baris yang memblokir kita
       const blockingReservation = await prisma.invitation.findFirst({
         where: { organizationId: orgId, normalizedEmail: email, acceptedAt: null, revokedAt: null }
       });
       
       // Cek apakah ini Zombie (reservasi > 5 menit tanpa Clerk ID)
       if (blockingReservation && 
           !blockingReservation.clerkInvitationId && 
           blockingReservation.reservedAt < new Date(Date.now() - 5 * 60 * 1000)) {
         
         // Hapus Zombie dan coba insert lagi
         await prisma.invitation.delete({ where: { id: blockingReservation.id } });
         return await insertReservation(orgId, email); // Retry
       }
       
       // Jika bukan zombie, berarti memang ada undangan aktif yang valid
       throw new TeamOperationError(TeamErrorCode.INVITATION_ALREADY_ACTIVE);
     }
   }
   ```
   *Keuntungan:* Tidak perlu infrastruktur *background worker* tambahan. Sistem membersihkan dirinya sendiri secara *on-demand* saat ada user baru yang mencoba mengundang email yang sama.

#### B. Mengatasi "Split-Brain" (Revoke Clerk Gagal)
Jika finalisasi DB gagal, lalu aplikasi mencoba me-*revoke* undangan di Clerk tetapi API Clerk sedang *down*, reservasi lokal terhapus tetapi undangan di Clerk tetap hidup. Percobaan berikutnya akan membuat duplikat di Clerk.

**Solusi: Status Kompensasi Persisten (Persiapan untuk Task #67)**
Jangan hapus reservasi lokal di blok `finally` jika revoke gagal.
1. Tambahkan kolom `compensation_status` (`NONE`, `PENDING_REVOKE`, `REVOKE_FAILED`).
2. Jika DB gagal dan revoke Clerk juga gagal, ubah status menjadi `REVOKE_FAILED` dan **biarkan barisnya ada**.
3. Buat *Background Job* (menggunakan BullMQ, Inngest, atau pg_cron) yang berjalan setiap 5 menit, mencari baris dengan `compensation_status = 'REVOKE_FAILED'`, dan mencoba memanggil API Clerk kembali.
4. Baris baru boleh dihapus dari DB hanya setelah Clerk mengonfirmasi bahwa undangan tersebut berhasil dicabut.
