# Kriteria Audit Final — Task #67 (Revisi Kedua)

## Tujuan Inti

Kegagalan sementara dipulihkan secara otomatis. Kegagalan permanen atau retry yang habis masuk ke kondisi terminal yang aman, tetap memblokir penggunaan undangan, dan memerlukan pemulihan manual terotorisasi. Sistem menjamin **safe failure**, bukan keberhasilan otomatis tanpa batas.

---

## 1. State Machine Persisten

### Transisi Lengkap

```text
NONE
  → PENDING_REVOKE
      (saat finalisasi database gagal setelah Clerk berhasil membuat undangan)

PENDING_REVOKE | REVOKE_FAILED
  → REVOKED
      (revoke Clerk berhasil, atau respons semantik menunjukkan sudah tidak aktif)
  → REVOKE_FAILED
      (revoke Clerk gagal sementara — self-transition untuk retry berturut-turut)
  → REVOKE_PERMANENTLY_FAILED
      (revoke Clerk gagal permanen — 4xx non-retryable)
  → DEAD_LETTER
      (retry_count mencapai batas maksimum)

REVOKE_PERMANENTLY_FAILED | DEAD_LETTER
  → PENDING_REVOKE
      (hanya melalui retry manual terotorisasi oleh owner organisasi)
```

### Kriteria Tinggi

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 1.1 | State machine mengikuti transisi lengkap di atas tanpa pengecualian | Tes state machine: setiap transisi legal valid, setiap transisi ilegal ditolak |
| 1.2 | Self-transition `REVOKE_FAILED → REVOKE_FAILED` didukung untuk retry berturut-turut yang tetap gagal sementara | Tes: 3 retry gagal berturut-turut → status tetap `REVOKE_FAILED`, `retry_count` bertambah |
| 1.3 | Lease worker disimpan terpisah dari status bisnis: kolom `lease_owner`, `lease_expires_at`, `claim_token` | Schema database menunjukkan kolom terpisah |
| 1.4 | Transisi status atomik dalam transaksi database | Tes konkurensi: 2 worker coba transisi bersamaan, hanya 1 berhasil |
| 1.5 | Worker yang crash di tengah transisi tidak meninggalkan status ambigu | Tes: kill proses saat update status, restart → status konsisten |

### Kriteria Sedang

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 1.6 | Timestamp setiap transisi dicatat (`compensation_updated_at`) | Query menunjukkan waktu perubahan |
| 1.7 | Alasan transisi dicatat (`compensation_reason`): `FINALIZATION_FAILED`, `REVOKE_RETRYABLE`, `REVOKE_PERMANENT`, `RETRY_EXHAUSTED`, `RETRY_SUCCESS`, `MANUAL_OVERRIDE` | Nilai enum sesuai |

## 2. Atomic Claim & Idempotensi (Tanpa Asumsi Idempotency Key Clerk)

### Predicate Claim

Worker mengklaim job dengan query atomic berikut:

```sql
UPDATE invitations
SET 
  compensation_status = compensation_status, -- tetap sama (PENDING_REVOKE atau REVOKE_FAILED)
  lease_owner = $worker_id,
  lease_expires_at = NOW() + $lease_duration,
  claim_token = gen_random_uuid(),
  compensation_updated_at = NOW()
WHERE id = $invitation_id
  AND compensation_status IN ('PENDING_REVOKE', 'REVOKE_FAILED')
  AND next_retry_at <= NOW()
  AND (lease_expires_at IS NULL OR lease_expires_at <= NOW())
RETURNING id, claim_token, clerk_invitation_id;
```

Jika `RETURNING` kosong, worker tidak mendapat lease dan langsung berhenti.

### Kriteria Tinggi

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 2.1 | Predicate claim mencakup `lease_expires_at IS NULL` agar job baru (tanpa lease sebelumnya) dapat diklaim | Tes: job baru dengan `lease_expires_at = NULL` berhasil diklaim |
| 2.2 | Predicate menggunakan `<=` (bukan `<`) untuk `lease_expires_at` dan `next_retry_at` | Audit query SQL |
| 2.3 | Atomic update menghasilkan `claim_token` baru, mengisi `lease_owner` dan `lease_expires_at`, mengembalikan baris yang diklaim | Tes: RETURNING mengembalikan baris dengan claim_token baru |
| 2.4 | Finalisasi hanya dilakukan oleh worker yang masih memegang `claim_token` yang sama | Tes: finalisasi dengan claim_token berbeda → ditolak |
| 2.5 | Lease dibersihkan setelah finalisasi berhasil atau gagal (set `lease_owner = NULL`, `lease_expires_at = NULL`, `claim_token = NULL`) | Tes: setelah finalisasi, kolom lease NULL |
| 2.6 | Respons Clerk yang secara semantik menunjukkan undangan "sudah tidak aktif", "tidak ditemukan", atau "sudah dicabut" diperlakukan sebagai keberhasilan idempoten → status = `REVOKED` | Tes: mock error sesuai SDK Clerk → status = `REVOKED` |
| 2.7 | Retry hanya untuk status `PENDING_REVOKE` atau `REVOKE_FAILED` | Tes: coba claim job `NONE` → tidak ada baris dikembalikan |

### Kriteria Sedang

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 2.8 | Tes meniru bentuk error sebenarnya dari versi Clerk SDK yang dipakai, bukan asumsi status HTTP | Audit test menunjukkan mock error sesuai SDK |

### Batasan Eksplisit

- Tidak perlu idempotency key untuk revoke (kecuali SDK Clerk terbukti mendukung)
- Tidak perlu distributed lock (optimistic locking via lease sudah cukup)

## 4. Klasifikasi Kegagalan (Konsisten, Tanpa Kontradiksi)

### Kategori Klasifikasi

| Kategori | Kondisi | Hasil Status |
|----------|---------|-------------|
| **Terminal-success** | Respons semantik Clerk menunjukkan: not found, already revoked, atau inactive | `REVOKED` |
| **Retryable** | Timeout, network error, HTTP `408`, HTTP `429`, HTTP `5xx` | `REVOKE_FAILED` (self-transition, retry berlanjut) |
| **Permanent** | HTTP `4xx` lain yang menunjukkan request atau otorisasi tidak dapat berhasil tanpa perubahan | `REVOKE_PERMANENTLY_FAILED` |
| **Unknown** | Error yang tidak terklasifikasi di atas | Default ke retryable dengan batas retry, kecuali kontrak SDK membuktikan permanen |

### Kriteria Tinggi

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 4.1 | Klasifikasi mengikuti tabel di atas tanpa kontradiksi internal | Audit: setiap jenis error dipetakan ke tepat satu kategori |
| 4.2 | `429` diklasifikasikan sebagai retryable, bukan permanent | Tes: mock 429 → status = `REVOKE_FAILED` |
| 4.3 | Untuk `429`, waktu retry menghormati header `Retry-After` jika tersedia; jika tidak, gunakan backoff panjang yang dibatasi | Tes: mock 429 dengan `Retry-After: 60` → next_retry_at = NOW() + 60s |
| 4.4 | Job `REVOKE_PERMANENTLY_FAILED` tidak di-retry otomatis | Tes: worker tidak claim job dengan status ini |
| 4.5 | Error `Unknown` default ke retryable, bukan permanent | Tes: mock error tak dikenal → status = `REVOKE_FAILED` |

### Kriteria Sedang

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 4.6 | Error message Clerk disimpan untuk debugging (tanpa token) | Audit log menunjukkan error message |

### Batasan Eksplisit

- Tidak perlu circuit breaker
- Tidak perlu klasifikasi granular di luar empat kategori di atas

## 5. Backoff, Retry Limit, & Dead-Letter

### Kriteria Tinggi

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 5.1 | Retry memakai exponential backoff (1s, 2s, 4s, 8s, ...) | Tes: cek delay antar retry |
| 5.2 | Backoff memiliki batas atas (max 5 menit) | Tes: retry ke-10 masih delay 5 menit |
| 5.3 | Batas retry maksimum (default 10 kali) | Tes: setelah retry ke-10 gagal → status = `DEAD_LETTER` |
| 5.4 | Job `DEAD_LETTER` tidak di-retry otomatis | Tes: worker tidak claim job `DEAD_LETTER` |
| 5.5 | Transisi ke `DEAD_LETTER` terjadi saat `retry_count >= max_retries` dan retry terakhir gagal | Tes: retry_count = 10, gagal → status = `DEAD_LETTER` |

### Retry Manual — Kontrak Eksplisit

| Precondition | Aksi |
|-------------|------|
| Status harus `DEAD_LETTER` atau `REVOKE_PERMANENTLY_FAILED` | Tolak jika status lain |
| Tidak ada lease aktif (`lease_expires_at IS NULL OR lease_expires_at <= NOW()`) | Tolak jika lease masih aktif |
| Request terautentikasi sebagai owner organisasi yang sesuai | Tolak jika bukan owner atau org berbeda |
| Filter query mencakup `organization_id` | Wajib |

| Perubahan | Nilai |
|-----------|-------|
| `compensation_status` | `PENDING_REVOKE` |
| `retry_count` | `0` |
| `next_retry_at` | `NOW()` |
| `lease_owner` | `NULL` |
| `lease_expires_at` | `NULL` |
| `claim_token` | `NULL` |
| `compensation_reason` | `MANUAL_OVERRIDE` |
| `compensation_updated_at` | `NOW()` |
| Error terakhir | Dipertahankan untuk audit (tidak dihapus) |

| Audit Log | Field |
|-----------|-------|
| Actor | User ID owner yang melakukan retry |

## 6. Safety: Undangan Terkunci Selama Kompensasi

### Jaminan Realistis

Database lokal menjamin hal-hal berikut. Sistem **tidak** mengklaim status eksternal Clerk sudah sinkron sebelum Clerk mengonfirmasi revoke.

### Kriteria Tinggi

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 6.1 | Endpoint acceptance menolak undangan dengan status `PENDING_REVOKE`, `REVOKE_FAILED`, `REVOKE_PERMANENTLY_FAILED`, dan `DEAD_LETTER` | Tes: coba accept untuk setiap status → ditolak |
| 6.2 | Undangan status kompensasi tidak dapat menghasilkan membership lokal | Tes: accept ditolak → tidak ada baris membership |
| 6.3 | Undangan status kompensasi tidak muncul di daftar undangan aktif | Tes: GET `/invitations` tidak mengembalikan |
| 6.4 | Email undangan status kompensasi tidak dapat diundang ulang sampai kompensasi selesai (`REVOKED`) atau dipulihkan resmi | Tes: coba invite email sama → error "compensation in progress" |
| 6.5 | Worker tetap mencoba revoke di Clerk sesuai kebijakan retry untuk status `PENDING_REVOKE` dan `REVOKE_FAILED` | Tes: job `REVOKE_FAILED` di-claim dan diproses worker |

### Kriteria Sedang

| # | Kriteria | Cara Verifikasi |
|---|----------|-----------------|
| 6.6 | UI menampilkan pesan jelas jika user coba accept undangan yang sedang dikompensasi | Tes UI: pesan "Undangan sedang diproses" |

### Batasan Eksplisit

- Database lokal tidak dapat menjamin Clerk sudah menonaktifkan undangan jika revoke gagal
- Sistem tidak mengklaim sinkronisasi eksternal sebelum konfirmasi Clerk
- Tidak perlu email notifikasi ke user tentang status kompensasi
